# Модуль LLM

Модуль хранит версии промптов и журнал вызовов, вызывает OpenAI-совместимый API и разбирает текст пунктов. Разбор идёт через `service.parse_text`, поэтому для него действуют общий дедлайн, повтор запроса и проверка результата.

## Промпты

- `GET /api/v1/admin/prompts?task=parse` возвращает версии выбранной задачи, новые первыми; у каждой версии есть `created_by`
- `POST /api/v1/admin/prompts` создаёт неактивную версию
- `POST /api/v1/admin/prompts/{prompt_id}/activate` делает её единственной активной для своей задачи
- Старый `/api/v1/admin/llm/prompts` оставлен скрытым совместимым маршрутом

Ручки требуют `X-Admin-Token`.

## Разбор пунктов

После commit API ставит Celery-задачу только для пункта `draft`. Worker не обрабатывает встречу со статусом `sent`. Результат применяется под блокировкой пункта, только если поле пустое и отсутствует в `manual_fields`. Для пункта, принятого на встрече, не меняются `what`, `assignee_person_id`, `due_date`, `due_text` и `done_criteria`; предметное поле «Срок» хранится парой `due_date` и `due_text`.

Когда значения изменились, версия пункта растёт, в журнал добавляется системное событие с `by=llm`, а панель получает `item.updated` и, если пересчитались пробелы, `gaps.updated`. Флаг завершения сохраняется вместе с изменениями или no-op в той же транзакции БД; Redis нужен только для защиты от параллельного запуска. Повторная доставка после commit проверяет флаг до LLM-вызова. Если worker падает до commit шага применения, более ранний LLM-вызов и его запись в `llm_calls` могут повториться.

## Доступ к провайдеру

Для реального вызова нужны `LLM_API_KEY` и `LLM_MODEL`. В production дополнительно требуется `LLM_DPA_CONFIRMED=1`, что означает подтверждение договора поручения с провайдером, а не согласие пользователя на обработку его данных. При отсутствии подтверждения сервис использует заглушку. На стенде с `DEV_MODE=1` сохраняется текущее поведение.
